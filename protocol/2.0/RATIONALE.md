# 原因层 · 我们为什么这么定

> 这份文件**只回答"为什么"**。规则本身在定义层（[DEFINITION.md](DEFINITION.md)）与协议自带规则（[RULES.md](RULES.md)）；做法在建议层（[SUGGESTIONS.md](SUGGESTIONS.md)）。
> **不在这里复述规则原文**——同一件事有两个版本，第一个上当的是下一个读它的人。
> 这份文件**只服务定义层**：解释"这些断言为什么必须这样"，不解释建议层的默认值。

## 一、它要解决的问题（换一个视角看同一件事）

> **这份框架最初是写给一个 AI 读的。以下全部出自它的位置。**

**问题不是"它不够聪明"，是它分不清"我记得"和"我知道"。**

它的错误有一个共同形状：**错的时候感觉良好。**

- 把**结论**当初记下来（"这个工作区里 pwsh 跑不了命令"），前提变了它不知道；
- 把**工具的限制**说成**世界的限制**（说出"环境不是一个"）；
- 把**别人的东西**当成**没有过**（旁边躺着一份 274 行的报告，它从零重做，还差点盖掉人家的权限修复）；
- 把**自己的猜测**当成**结论**卖出去（三条旧猜测全是假设，后来一条条被推翻）。

一个会话里的 AI 没有稳定的立足点：**它的上下文会满、会被压缩遮蔽、会话结束它就没了。** 于是"我上一次确认过 X"这件事，下一次它无从校验。

**协议就是在这里用的**：它不企图把 AI 变聪明，它给 AI 一批**能重新算一遍的前提**——

- 需要先知道**什么算事实**（实测 / 声明 / 人证 / 推断要分标）；
- 需要先知道**东西归谁**（我的认知 / 参考信息 / 工具）；
- 需要先知道**"能不能用"不是事实**，是算出来的（所以不许写下来当结论）。

## 二、为什么定义是"环境 = 信息 + 工具"

**从目标往下派生的顺序**（每一句都是上一句逼出来的）：

1. **目标**：让 AI 从会话里脱离出来，成为一个可被托付的助手。
2. → 要脱离会话，就必须有一个**不随会话生灭的立足点**。那就是**工作区**——它在，会话只是它的一次投影。
3. → 工作区要能被核算，就得分开两样东西：**它知道什么**（信息）、**它能对它做什么**（工具）。
4. → 两样相遇才有"能不能用"，所以**可用性不落盘**，用时现算。
5. → 信息要能被信任，就得先分**归属**（自有的 / 外部的）——因为**认识不能假借**，只有它自己认过的才算它的。
6. → 能力要能被重复，就得**落地成工具**——散在命令行里的动作，下一个它找不到。

**顺序不能反。** 先给定义、再让人猜目标，读的人（包括下一个 AI）会先拿到分类工具，再自己脑补它要解决什么。

**为什么定义层不许改**：它是这一串派生的**根**。动根，下面每一条的来历都会失真，而失真不会报错——只会静默地长出"看起来对"的规则。有不同意见，改建议层，或者换一份新定义。

## 三、为什么信息要分归属

自有的信息 = **我的认知**：认识不能假借——只有它自己认过的才算它的，所以它负责。外部的信息 = **参考**：默认只读、通常不建议改，它不是我的认知。

不这么分，AI 会把"别人的东西"当成"我知道的"，也会把没有认过的东西写成结论。工作区因此必须有自我认知库 + 外部信息库。

## 四、为什么把日记、决定从自我认知里分出来

**日记是"选出来的"，不是历史。** 它的价值不在"全"，在"以后还用得上"：如果每句话都记，日记会退化成第二个历史库——读不完、找不到、也不会有人维护。真正该留下的，是以后会改变判断或行动的东西。

**决定不是认知。** 决定属于某个时刻、有明确范围和局限、可能被新事实推翻；认知回答"我认过什么、我相信什么"，决定回答"当时在几个选项里选了什么、为什么"。把决定塞进认知库，会把"我做过一个临时选择"变成"我就是这么认为的"——前者可以推翻，后者会被当成身份的一部分，改起来有心理负担，也容易把旧决定带进新情景。

**决定放在日记下**，是因为它们共享同一条时间轴：日记记录"那段时间发生了什么"，决定记录"其中哪一个选择值得单独留下来"。放在两个顶层库里，时间会被切成两套。

## 五、为什么历史留在宿主、不进工作区

完整对话原文已经被宿主保存了。工作区再存一份，会有三个问题：

1. **重复**：同一份原文有两个版本，迟早对不上；
2. **成本**：完整历史很大，日常读它会把注意力从"可复用的认识"拉回"逐字复现"；
3. **误导**：存了全文，就会误以为"读过全文"等于"知道了"，而知道需要提取和判断。

所以历史留在宿主，工作区只放**从历史里挑出来的重要内容**。日记不是历史，是对历史的取舍。

## 六、为什么规则要单独成类、规则库是当前约束的唯一来源

**约束散落会出三个问题**：不可审计（不知道总共有哪些约束）、不可触发（不知道某个情景该加载哪几条）、不可失效（旧约束被推翻后没有状态可改）。规则库不是因为它"更高级"，而是因为它**可枚举、可索引、可标状态、可按范围查**。

**规则不是决定的投影**：决定只是规则的来源之一；规则还可以来自共识、用户、外部文档、定义派生、自我承诺。把规则库做成决定库的副本，会把"共识"和"轻量约定"排除在外，也会逼着每条规则都编一个决定。

**规则总是关于某个适用范围的**：不同情况下规则不同，规则就会膨胀；这正是需要一个规则库统一处理的原因——按适用范围组织和取用，而不是把规矩各自塞在文档里。

**唯一来源的意思是**：当前对行动有强制力的约束都能在规则库里找到，并且能在那里被标状态、被替换。决定和日记可以解释规则，但不能代替规则。

## 七、为什么规则库要自带一条"遵守协议"的规则

"协议当然要遵守"这件事，一直是默认的：它不在任何可枚举的地方，所以没法被引用、没法被核对。

而规则库是当前行动约束的唯一来源——如果"遵守协议"不是一条规则，这个唯一来源就是一句悬空的话：它管不住"为什么要遵守它"。所以版本自带一条"任何情况下遵守协议"的规则，采用版本时进入规则库。这有两个作用：

- 把默认遵守的前提第一次显性化；
- 定义层的约束力由此闭合：遵守协议 → 协议里的定义与规则都生效——**不需要另写"定义层在规则库之上"**。

## 八、哪些是借来的、哪些还没定

**"环境 = 信息 + 工具"推不出下面这些**，它们是从别处抱来的，必须知道自己抱了：

| 借来的 | 出处 | 为什么要明说 |
| --- | --- | --- |
| 对私人目录不做无目标递归枚举 | 用户的授权与隐私 | 定义推不出"不该翻别人桌面" |
| 机器级改动必须先问 | 人机分工 | 定义推不出"哪些动作要批准" |
| 不为了产生行为而行动 | 教训（"制造拒绝来铺路"） | 是纪律，不是派生 |

**抱来的不一定不对，但必须知道自己抱了。**

尚未定、本协议不替它发明的：

- 信息边界（入口 / 出口 / 寿命的细则）与回收条款；
- 决定库、规则库的操作细节（等实践）；
- 历史原文的引用方式（默认不读；要引用时怎么指回宿主）。

## 九、这份文件不做什么

- 不写规则（那是定义层与协议自带规则的事）；
- 不写"怎么做"（那是建议层与插件开发文档的事）；
- 它只保证一件：**任何人读到某条定义时，都能往回走到"它为什么必须这样"。**
